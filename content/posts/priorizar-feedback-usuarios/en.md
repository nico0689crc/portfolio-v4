Every product with real users gets a constant stream of feedback. The most common temptation is treating every request as if it carried the same weight, and they don't. Prioritizing user feedback is exactly that: deciding which one weighs more. Without that criteria, a focused product turns within a year into one trying to be everything to everyone.

## Prioritizing user feedback: first, who asked?

It isn't elitism. Different users represent different risks and opportunities. On [GymSmartAccess](/en/projects/gym-smart-access), feedback from an owner who's been paying for eight months carries different weight than from someone trying the free version a week ago. Not because one matters less as a person, but because one has already shown sustained commitment.

A request that represents a pattern, three different gyms asking for the same thing without coordinating, carries far more weight than an isolated one. No matter how convincing the isolated one sounds in the moment.

## The second: does this solve the underlying problem, or the symptom someone reported?

When someone asks for a specific feature, they're almost never describing the right solution. They're describing the only one that occurred to them, with partial knowledge of the system. My job is to understand the problem behind the request, not to literally execute it. It's [jobs to be done](https://hbr.org/2016/09/know-your-customers-jobs-to-be-done) applied to support.

An owner asking to "send a mass message to all members" probably doesn't need a messaging system. They need to announce a schedule change or a holiday, a much smaller problem than the requested solution suggests.

## The third: does this request compete with the product's core purpose, or reinforce it?

Every new feature passes the same test I described in [from idea to MVP](/en/blog/from-idea-to-mvp-what-to-build): if this didn't exist, would the product stop solving its main problem? If the answer is no, the request might still be valid, but it changes category. It moves from "essential" to "improves the experience", and competes with everything else in that category.

## What I discard outright, no negotiation

**Requests that only benefit an extremely specific, rare edge case.** Building for the 1% of edge cases at the cost of complicating the experience for the other 99% is an investment that almost never pays off.

**Requests that contradict the reason the product exists.** If GymSmartAccess exists to simplify billing and access, a feature that adds administrative complexity for the gym owner — even if someone asks for it — works against the core purpose, not for it.

**Requests where the person can't explain the underlying problem, only the solution they imagined.** When I ask "what do you need that for?" and the answer is vague, it usually means the request doesn't come from a recurring problem but from a loose idea.

## How I communicate that something won't get built

I don't say "no" without explanation: that makes feedback feel pointless and cuts off the flow. I explain why the request isn't going in at this stage. Because it doesn't solve the core problem, because it affects very few cases, or because there's a simpler solution for the underlying problem. Whoever asked leaves knowing they were heard, even if the answer is no.

## Where the unbuilt requests go

None of this gets discarded into thin air. Every request that doesn't make the cut is logged with a date and who asked, in a list I review every couple of months.

It serves two purposes. The first is catching patterns that take time to form: an isolated request in March and another in July are the same request if nobody wrote them down. The second is not relitigating the same discussion from scratch when it comes back.

## The mistake that's hardest to avoid

Whichever client shouts loudest, or holds the most weight in the business relationship, wins by default if there's no explicit criteria. Having the three questions written down is what lets me say no to an insistent request without it feeling arbitrary. Not to me, and not to whoever asked.
